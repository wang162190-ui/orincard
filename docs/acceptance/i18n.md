## 一、S12 · 会话穿过语言协商不掉

这是本阶段唯一真正危险的一步。`src/proxy.ts` 里两件事必须在同一个 response 上完成：Supabase 的会话刷新，和 next-intl 的语言协商。

**顺序是有意的**：Supabase 先跑，把轮换出来的 cookie 写回 `request.cookies`，next-intl 与下游 Server Component 才读得到刷新后的会话；然后把这批 cookie 写到 **next-intl 产出的那个 response** 上。

失败模式很安静：next-intl 在语言协商时常返回 **307**（带 `NEXT_LOCALE` 的用户访问 `/pricing` 会被送去 `/zh-Hans/pricing`）。此时若另起一个 `NextResponse.next()` 写 cookie，redirect 丢失；若直接返回 next-intl 的 response 而不补 cookie，**轮换后的 token 就在这一跳里蒸发，用户一切语言就掉登录**。

真实验收（`tests/e2e/locale-session.spec.ts`，`ORINCARD_RUN_LOCALE_E2E=1`，真账号打 `:3000`）：

```
登录 → /api/v1/projects            200
切到 /zh-Hans/projects             未跳 /login，html lang="zh-Hans"
中文侧 /api/v1/projects            200      ← 会话活着穿过了语言协商
访问 /projects                     307 → /zh-Hans/projects
显式切回 en 后 /api/v1/projects    200
```

**变异验证**（`tests/unit/i18n-proxy.test.ts`，24 条）：把 cookie 改写到另起的 response 上 → redirect 与 rewrite 两条用例立刻转红。

### 顺带确认的一条行为：语言选择被 cookie 记住

选过中文之后，无前缀的 `/projects` 会 **307 到 `/zh-Hans/projects`**。这是 next-intl 的刻意行为（`NEXT_LOCALE` cookie），不是回退失败 —— 对已选中文的用户，无前缀 URL 不再是英文入口。搜索引擎没有这个 cookie，仍然看到英文版。我最初的验收断言写错了方向，按实测行为改正并记在这里。

### `/api/**` 绝不参与语言协商

next-intl 的 middleware 会把它看到的一切改写成带 locale 的路径。`/api/v1/projects` 一旦被改写成 `/en/api/v1/projects`，**48 条 API 路由会一次性 404**。

`src/proxy.ts` 的 `NON_LOCALIZED_PREFIXES` 把 `/api`、`/auth`、`/robots.txt`、`/sitemap.xml` 排除在语言协商之外，但**仍然让它们走会话刷新**——不参与语言协商不等于不刷新会话。实测 `/api/v1/projects` 返回 **401**（认证不足）而不是 404，说明路由没被改写。**变异验证**：去掉这个判断 → 5 条用例转红。

## 二、S13 · 私有路由与 SEO

`isPrivateRoute` 原本按前缀精确匹配，加了语言前缀后 `/zh-Hans/billing` 匹配不上 `/billing`。这个缺陷不会报错，只会让中文账单页**从此可被收录**。已改为先剥 locale 段再匹配（`stripLocale`，只剥注册过的 locale，`/zh/billing` 里的 `zh` 不吃）。

实测 HTTP 头：

```
/billing           x-robots-tag: noindex, nofollow
/zh-Hans/billing   x-robots-tag: noindex, nofollow
/pricing           (无)
/zh-Hans/pricing   (无)
/fr/pricing        404          ← 未注册语言不静默回落
```

`/fr/pricing` 返回 404 而不是渲染英文页：否则会凭空多出一批与 hreflang 对不上的可索引 URL。

**robots.txt** 现在按语言各写一遍 disallow（13 个私有前缀 × 2 语言 = 26 条）。只写 `/billing/` 的话，`/zh-Hans/billing/` 不受任何约束。

**sitemap.xml**：10 条路径 × 2 语言 = **20 条 URL**，每条带 `en` / `zh-Hans` / `x-default` 三个 `xhtml:link`。`x-default` 指向英文版，与 `localePrefix: 'as-needed'` 一致。

**canonical 跟随当前语言**：中文页的 canonical 指向中文 URL。若两个语言版本互相指认对方是正本，hreflang 与 canonical 自相矛盾，搜索引擎会忽略整组声明。

## 四、S15 · 界面字符串抽取（上半）

`messages/en.json` 与 `messages/zh-Hans.json` 各 **15 个命名空间、key 集合一致**（S16 会加测试把这句话变成断言，现在还只是人工核对）。18 个文件改用 `useTranslations` / `getTranslations`。

### 判据：切换器在真实浏览器里真的能切，且切过去确实是中文

`tests/e2e/marketing.spec.ts:20` 的 `S15 switches the rendered language from the public header`，**2 passed**：

```
/pricing → 选 zh-Hans → URL /zh-Hans/pricing、html lang="zh-Hans"、
            h1 = "先免费开始。付费套餐可加入等候名单。"、方案名 = "创作者版"
         → 选 en     → URL /pricing、html lang="en"、h1 回到英文
```

断言里同时查了「**同一条路径**的中英两版落在同一个页面上」——切语言把人丢回首页是这类实现最常见的错法。

单测里 `useRouter` 是被 mock 掉的（jsdom 没有挂载的 app router），所以**切换器能不能用，只以上面这条浏览器用例为准，不以 mock 为准**。

### 英文必须逐字节不变

`tests/e2e/{marketing,growth,support,billing,accessibility}.spec.ts` 断言的是精确英文串。`messages/en.json` 里每个英文值都是从它替换掉的那个字符串**原样拷来的**，不是重写的。实测 `/` 上的 href 集合仍是 `['/', '/create', '/login', '/pricing', '/pricing#waitlist', '/tools']`，一个没变。

### 抽取过程中修掉的一个真实缺陷：两个控件都叫 "Language"

切换器最初的可访问名是 `Language`，和创作页的**生成语言**字段撞名。`accessibility.spec.ts` 在 chromium/firefox/webkit 上各报一次 strict mode violation（`resolved to 2 elements`）。

这不是测试挑剔——同一页上两个同名控件，屏幕阅读器用户无法区分「界面语言」和「生成内容的语言」，是真的 a11y 缺陷。改名为 **Interface language / 界面语言**（生成语言字段保持 `Language / 语言` 不变）。改后 `accessibility.spec.ts` + `marketing.spec.ts` 三浏览器 **29 passed / 2 skipped**。

顺带把 `marketing.spec.ts` 的选择器改成 `exact: true`：Playwright 的 `name` 默认子串匹配，`"Language"` 照样能命中 `"Interface language"`——正是这种宽松匹配让重名缺陷从这条用例底下溜了过去。

### 一处刻意不走 next-intl `Link` 的地方

定价页的页内锚点 `href="#waitlist"` 用的是**普通 `<a>`**。next-intl 的 `Link` 会给它加语言前缀，把一个同页跳转变成跨页导航。跨页的 `/pricing#waitlist` 仍用 next-intl `Link`，中文站实测渲染成 `/zh-Hans/pricing#waitlist`，正确。

### 测试用真实词条渲染

`tests/ui/{shell,editor}.test.tsx` 把被测组件包在 `<NextIntlClientProvider locale="en" messages={require('messages/en.json')}>` 里。这样断言里的英文来自词条文件本身，**key 打错或漏翻会直接让用例失败**，而不是悄悄渲染出一个占位符。

### 三处「不是组件，但也得翻译」的处理

抽取过程里撞上三类拿不到 `useTranslations` 的代码，各自的做法和理由：

1. **模块级函数抛 key，由 React 侧翻译。** `source-input.tsx` 的轮询与上传是模块级函数。给 `SourceFailure` 加了一个 `messageKey` 字段，表单的 catch 处统一 `t(failure.messageKey)`。**服务端回传的 message 仍原样透传**——那是服务端文案，是另一层的问题，本步不假装解决。
2. **翻译函数当参数传。** `editor-media.tsx` 的 `asMedia()` 要产出可访问名（如 "Pexels image · stock"），`editor.tsx` 的 `createStarterDocument()` 要产出起始文档正文。两者都从调用处把 `t` 传进去。
3. **注册表加 `messageKey` 并行字段。** `MEDIA_SOURCES`、`TABS`、`MODES` 保留原来的英文 `label` 作稳定标识（测试和日志用），另加 `messageKey` 供界面渲染。

起始文档（`createStarterDocument`）严格说是**内容**不是界面 chrome，但它是空白编辑器里唯一的字，留着英文等于中文站开箱即英文，所以一并翻了。

### 测试补 Provider 的两个坑

- **用 RTL 的 `wrapper` 选项，不要手动套一层 Provider。** `rerender` 会自动沿用 `wrapper`，手动套的那层不会——`media.test.tsx` 用到 `rerender`，手套会在第二次渲染时炸掉。6 份测试统一改成 `wrapper`。
- **`getTranslations` 在 vitest 里不能用。** 没有 Next 的请求作用域，它会解析到 `react-client` 条件下那个直接抛 "is not supported in Client Components" 的桩。写了 `tests/helpers/intl-server.ts` 补请求上下文，**词条仍从真实的 `messages/*.json` 读**，所以 key 打错照样红，桩没有削弱断言。

### S15 推迟的五类页面，外壳在本步提前做了

S15 把 `templates/`、`tools/`、`help/[slug]`、`guides/[slug]`、`legal/[slug]` 整体推到 S17，理由是「只翻外壳会做出半中半英的页面」。本步的判断不同：**它们的外壳是界面，不是内容**，属于 S16 的定义范围；留到 S17 只会让 S16 的「src 下无硬编码英文」判据没法成立。

所以现在这五类页面是**中文外壳 + 英文正文**的中间态。这正是 S15 警告过的形态，是有意为之，S17 补上 `content/*` 的中文正文后收口。**不把它算作完成。**

## 六、S17 · 内容文件双语

界面翻完之后，中文站上剩下的英文就集中在 `content/` 的正文里——`help` 三篇、`guides` 一篇、`legal` 三份。本步把这 7 份补上中文，并把工具注册表的 7 个工具名一起收掉（S15 起就挂在那）。

### 文件怎么摆：英文原地不动，中文放镜像目录

| 语言 | 路径 |
|---|---|
| en | `content/help/getting-started.mdx`（**一个字节都没动**）|
| zh-Hans | `content/zh-Hans/help/getting-started.mdx` |

### 缺中文文件时**不回落英文**

`readContent(kind, slug, locale)` 读不到对应语言的文件就抛 `ContentNotFoundError`，不去读英文那份。回落看起来更"稳"，实际是把漏翻藏起来：页面照样 200，只是中文用户读到一整页英文，而且没有任何信号。

漏翻由 `tests/unit/content-locales.test.ts` 在构建前拦下，**10 passed**，断言四件事：

1. 目录里每一条（7 条）在两种语言下都有文件，且都能被 `parseTrustedMarkdown` 解析通过；
2. 每份文档的 `title` 与 `description` 中文版**不等于**英文版（照抄英文会红）；
3. 三份法律文本的 `policyVersion` 与 `publicationStatus` 两语言一致，而 `contentHash` 必须不同（同 hash 说明根本没翻）；
4. 缺文件时确实抛错，而不是回落。

## 七、S18 · 生成语言枚举 + PPTX 中文字体（含阶段二完成判据）

### 7.1 语言：自由文本 → 枚举

改之前 `src/features/generation/options.tsx` 是个 `maxLength=80` 的自由输入框，`src/server/generation.ts` 的 `language` 是 `string`。也就是说「中文」「zh」「Chinese, please」全都能提交，模型对每种写法的反应不一样，导出侧也没法据此判断该用哪套字体——**没有枚举就谈不上「按语言验收」**。

现在 `GENERATION_LANGUAGES = ["en", "zh-Hans"]`，`isGenerationLanguage()` 同时把住 `validateOptions` 与 `POST /api/v1/generation` 两道口。

有一处值得单独说：prompt 里传的**不是** `zh-Hans` 这个代码，而是整句 `"Simplified Chinese (简体中文). Write every field in Simplified Chinese."`。模型见过的 "Simplified Chinese" 远多于 "zh-Hans"，后者有时会被当成一个无意义的标签而整份输出英文。`tests/unit/generation-language.test.ts` 直接断言替换后的指令文本，把这件事钉住。

变异验证（两条，各自跑过红再恢复绿）：

| 变异 | 结果 |
|---|---|
| `isGenerationLanguage` 放宽成「任意非空字符串」 | **14 中 7 条失败** |
| prompt 里改回传裸 `options.language` | **1 条失败** |

**真调了一次供应商**（`tests/cloud/generation-language-live.test.ts`，`ORINCARD_RUN_GENERATION_CLOUD=1` 才跑）：英文源文 + `language: "zh-Hans"` → 六页，每页标题都含中文，且正文里没有 25 字符以上的连续英文段。断言写成「逐页检查」而不是「整体含中文」，否则模型只翻第一页也能蒙混过关。

### 7.2 PPTX 的中文字体：真实缺陷，已修

PNG / JPG / PDF / MP4 都走浏览器渲染，字体栈里有 Noto Sans SC，中文一直是正常的。**只有 PPTX 不嵌字体**——它把字体名写进文件，由 PowerPoint 自己去找。原来写的是 `Inter` / `Source Serif 4`，两个都没有一个汉字，于是中文只能落到阅读器自己的默认 CJK 回退字体，而且**粗体属性会一起丢掉**。

修法：`deckHasCjk()` 扫整份文档（标题、eyebrow、CTA、所有正文块），命中就让 `fontFace()` 返回 `Noto Sans SC`。判定按整份文档而不是按页，因为一份英文稿里混进一个中文词（品牌名、引文）就足以触发回退。

同时给 `font-manifest.json` 补了 Noto Sans SC **700**：中文标题是粗的，只嵌 400 的话浏览器会合成伪粗体，笔画糊成一团，而且和 PPTX 里 PowerPoint 解析出的真 Bold 对不上。`docs/licenses/assets.md` 与 `docs/licenses/fonts.md` 的 OFL 归属已同步补上 700 这一行——**漏了会真的挂**：补之前 `release-guards.test.ts` 从基线的 5 条失败涨到 6 条，多出来的正是「字体清单与 manifest 对不上」。

补 700 时顺手修了一个连带问题：`preflight.ts` 的 `selectedFontFamilies()` 按 manifest 条目展开家族名，Noto Sans SC 有了两个字重之后同一个家族名会出现两次，等于向浏览器把同一个问题问两遍。用 `new Set()` 去重解决——**是改产品代码，不是把测试放宽**。

实测对比（LibreOffice 转 PDF 后光栅化，两份都在这台机器上出）：

| | slide1.xml 里的 `typeface` | 标题呈现 |
|---|---|---|
| 修之前 | `Inter` / `Source Serif 4` | 中文能显示，但**是细体**——粗体属性在回退时丢了 |
| 修之后 | `Noto Sans SC` | 中文，**真粗体** |

## 八、选型与两处配置决定

- **`localePrefix: 'as-needed'`** —— 英文保持无前缀。已收录的英文 URL 与既有 `alternates.canonical` 一个都不变；改成 `'always'` 会让所有英文 URL 一次性变成 301，且与既有 canonical 自相矛盾。
- **`vitest.config.ts` 加 `server.deps.inline: ["next-intl"]`** —— next-intl 的 ESM 产物写的是 `import ... from "next/server"`（无扩展名），Node 原生 ESM 在 pnpm 的嵌套 store 里解析不到。让 vite 接管这个包的转换即可。这是测试环境的解析问题，不是产品代码问题。
- **`next.config.mjs` 支持 `NEXT_DIST_DIR`** —— 验证性构建换一个产物目录，免得覆盖正在被 `next start` 服务的 `.next`。不设时行为与以前完全一致。

## 九、诚实边界

> 这一节按步收敛过三次：S15 的「28 个 `.tsx` 硬编码英文」「key 靠人工核对」在 S16 已不成立；S16 的「`content/*` 正文只有英文」「工具 label 英文」在 S17 已不成立；S17 的「生成语言还是自由文本框」「PPTX 不返回 CJK 字体」在 S18 已不成立。都已删除，不留旧话。以下是 S18 结束时的真实边界。

1. **`content/templates.json` 仍是全英文**，7 个模板的名称、描述、以及模板自带的整份示例文档都是。**这是有意留下的**：它是 `release-guards.test.ts` 眼中的「发行物」（`EXTRA_ASSET_PATHS` 明确把它算作素材），多加一份中文模板库就要同步补权利登记，而那块正卡在 B-3 的素材清单上。所以中文用户打开模板库，看到的是中文外壳 + 英文模板。**没有当作做完。**
2. **服务端回传的错误文案仍是英文。** 前端的兜底文案翻了，但 API 路由与 Trigger.dev 任务回传的 `message` 是原样透传的——中文用户触发一个服务端错误，看到的仍然是英文句子。始终没在任何一步的范围内，也没有假装解决。
3. **三份中文法律文本是 `draft`，和英文一样。** 翻译只是把英文草稿的立场原样搬过来，**没有替你做任何一项商业决策**；12 项决策仍是 B-1。`release-guards.test.ts` 现在按两种语言查 6 个文件，所以中文站不可能绕过审定要求偷偷上线。
4. **PPTX 没有用真 PowerPoint 打开过。** 这台机器**没有安装 Noto Sans SC 系统字体**（`system_profiler SPFontsDataType` 查过），所以就算现在打开 PowerPoint，看到的也必然是回退字体——不是因为改错了，而是 **PPTX 这个格式本身不嵌字体**。我用 LibreOffice 转出的对比图证明了「字体名写对了、粗体不再丢」，但「和预览逐字形一致」这一条只有在阅读器装了 Noto Sans SC 时才成立。判据里「用 PowerPoint 真实打开」这一步**我没做**：`deck.pptx` 在 `/tmp/orincard-s18`，你双击一下就能确认。
5. **由此带来的产品问题，需要你决定**：PPTX 写 `Noto Sans SC`，和预览完全一致，但 Windows 与 macOS 都不预装它，收件人多半看到回退字体；换成 `PingFang SC` / `Microsoft YaHei` 这类系统自带家族则大多数机器都认，但**永远和预览对不上**，而且两个系统还不是同一个。当前按计划选了前者（仓库打包的就是它）。这是个产品取舍，我没有替你改。
6. **e2e 只在本机 `:3000` 的 dev server 上跑过**，没有在生产构建上跑（`:3100` 服务的是 9-11 的旧构建，按约定没有动它）。
